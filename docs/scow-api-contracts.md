## Authentication and setup

- [`GET /api/auth/validateToken`](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/auth/validateToken.ts#L18-L45) takes the raw SCOW_USER value in query `token`; success contains `identityId` and optional `name`; public rejection is `403 null`. On 2026-10-25 an authorized negative-only probe of the deployed endpoint observed HTTP 403, verified TLS, `application/json`, and zero response bytes. The client accepts that exact empty-JSON validator rejection as a verification gate too, without generalizing other 403 bodies/endpoints or inferring expiry. Identity fields are discarded.
- The public [token implementation](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/auth/token.ts#L27-L40) can also translate an internal auth-service failure into unsuccessful validation. A rejection is not proof that a token has expired. REST rejection gates new operations and prompts verification; it does not delete stored credentials.
- [`/api/setup`](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/setup.ts#L17-L30) installs WS listeners once per loaded server module and returns plain `Setup complete` or `Already setup`. It is unauthenticated, so its failure cannot establish token validity. The user already supplied a successful live observation; it was not repeated merely to confirm that report.
- [Cookie authentication](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/auth/server.ts#L24-L57) and file-operation errors differ. `401` is authentication rejection; file `403 PERMISSION_DENIED`/`NOT_ACCESSIBLE` and other authorization failures are permission errors, not automatic cookie-revocation evidence. Only the existing WSS 401/403 path automatically revokes credentials.

## Official file transport

Verified public routes: [download](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/file/download.ts), [upload](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/file/upload.ts), [initMultipartUpload](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/file/initMultipartUpload.ts), [mergeFileChunks](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/file/mergeFileChunks.ts), [fileExist](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/file/fileExist.ts), [list](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/file/list.ts), and [move](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/file/move.ts).

The deployed [upload client](https://107.ustc.edu.cn/_next/static/chunks/1412-96e2620f29ce9563.js), modules 20214/related upload caller, confirms:

- Multipart binary field is `file`. `chunk` and `originPath` are URL query parameters, not multipart text fields.
- Init JSON is `{cluster,path,name}`, with destination directory `path`; response supplies `tempFileDir`, `chunkSizeByte`, `filesInfo`.
- A chunk filename is `<sha256-of-raw-chunk>_<one-based-index>.scowuploadtemp`; chunk size comes from the server, not a client constant. [Deployed SHA-256 helper](https://107.ustc.edu.cn/_next/static/chunks/5448-1599fb54b20e06c1.js), module 25329, hashes raw bytes.
- Merge JSON is `{cluster,path,name,sizeByte}`; `sizeByte` is the complete original file byte length, not the block length/count.
- The production daemon path initializes multipart for every file and uploads sequentially. Its final-block progress approximation can overcount; this client must count exact acknowledged bytes.
- The observed private helper interpolates `originPath` without explicit encoding. This client uses URLSearchParams so reserved characters cannot become extra query parameters; it does not reproduce that unsafe interpolation.
- `PATCH /api/file/move` has JSON `{cluster,fromPath,toPath}` and public success 204. No inspected upload/init/merge/move contract supplies exclusive creation or conditional replacement.

### Existing destinations: rename is not overwrite

The pinned [SSH move backend](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-server/src/clusterops/file/sshFile.ts) invokes `sftpRename`; the pinned [helper](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/libs/ssh/src/sftp.ts) wraps **plain `sftp.rename`**, not `ext_openssh_rename`. [SFTP v3, section 6.5](https://www.ietf.org/archive/id/draft-ietf-secsh-filexfer-02.txt), specifies an error when `newpath` already exists. [Official ssh2 documentation](https://github.com/mscdex/ssh2/blob/master/SFTP.md) separately identifies `ext_openssh_rename` as POSIX rename(3). Therefore staging followed by `PATCH /api/file/move` does **not** establish replacement support. The SSH backend maps rename failure to gRPC `INTERNAL`; the [HTTP move route](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/file/move.ts) maps that to **415 `{code:"RENAME_FAILED",error:string}`**, not a collision-specific 409. The daemon adapter merely delegates `client.file.move({userId,fromPath,toPath})`; its server implementation and overwrite semantics are unavailable.

By contrast, the public [ordinary-upload route](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-web/src/pages/api/file/upload.ts) has no destination-existence/collision preflight, and the SSH backend calls **`sftp.createWriteStream(path)` without options**. ssh2 documents the default as **`flags:'w'`**: create/truncate, not exclusive creation. Direct ordinary upload is thus an evidenced **non-atomic overwrite-in-place** path on that backend. It can leave a truncated, partial, or changed destination after an error; receiving a complete local spool first and verifying a remote readback before success acknowledgement does not create a rollback guarantee. Neither the daemon upload adapter nor the [merge route/backend wrapper](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-server/src/services/file.ts) contains collision checks or an overwrite option, but the unavailable private daemon owns their actual write/merge behavior. The deployed browser's deletion-before-upload behavior is **not evidence** that those daemon operations themselves overwrite. No client deletion should be used to manufacture replacement support.

The TLS fixture therefore defaults **`moveOverwrite:false`**: moving onto an existing destination returns 415 `RENAME_FAILED` and preserves both files. Tests may explicitly select **`moveOverwrite:true`** to simulate a replacement-capable backend; such tests do not prove that the pinned SSH or deployed private backend supports rename replacement. Ordinary-upload replacement is modelled separately from rename capability. No private merge overwrite guarantee is inferred from the fixture's multipart round trips.

The [deployed API runtime](https://107.ustc.edu.cn/_next/static/chunks/pages/_app-3d8f1bcbda04c4f9.js) registers those GET/POST methods and paths. The [deployed file-manager chunk](https://107.ustc.edu.cn/_next/static/chunks/1412-96e2620f29ce9563.js), module 79876, calls `mkdir({body:{cluster,path:join(parent,name)}})` and handles 409; its upload caller compares `getFileType().type` to **lowercase `"dir"`**. Module 32954 consumes `mtime`, byte `size`, and `mode`, masking permissions with octal 777; its displayed directory type is uppercase `"DIR"`. Static JavaScript does not establish private-server field optionality or guarantee a successful directory mutation.

The pinned [SSH backend](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-server/src/clusterops/file/sshFile.ts) establishes the following details:

- `getHomeDirectory` obtains `sftpRealPath(".")`, rather than deriving `/home/<identity>`. SCP relative paths must resolve against the authenticated API's returned home, not a guessed username/home or an assumed daemon working directory. The [daemon adapter](https://github.com/PKUHPC/OpenSCOW/blob/8de039b22c51f99c06d59f4337a962ceb46f85dd/apps/portal-server/src/clusterops/file/scowdFile.ts) also exposes an explicit home lookup; relative paths passed directly to daemon file operations have no recovered working-directory contract.
- `makeDirectory` performs existence preflight followed by **one `sftpMkdir`**. It does not recursively create missing parents. The daemon adapter passes a single `dirPath`; it supplies no documented recursive-parent or no-follow guarantee. Parent checks and a later mkdir can race.
- `readDirectory` validates the requested directory using **`sftpStat`**, then maps SFTP directory entries. A name is labelled `DIR` only when `longname` starts with `d`; every other kind, **including a symlink**, is labelled `FILE`. It preserves the entry's raw `attrs.mode` (including POSIX file-kind bits), `attrs.size` in bytes, and `new Date(attrs.mtime * 1000).toISOString()`. `mtime` is modification time, not access time or a separate change-time field. `updateAccessTime=true` may issue `touch -a`; this client always sends false.
- `getFileMetadata`/`getFileType` use **stat**, not lstat, and report `dir` or `file`; they cannot establish that a path is not a symlink. Download/open operations are not evidenced as no-follow. The daemon adapter passes `modTime`, `mode`, `Number(sizeByte)` and the `fileType` mapping through; the private daemon's symlink treatment and complete mode encoding are not established by this adapter or deployed JavaScript.

The file adapter validates listing names as unique, nonempty single components (no dot/dotdot, separators or control characters), timestamps as finite ISO-style strings, modes as unsigned 32-bit integers, and sizes as nonnegative safe integers. It returns only the five evidenced fields and preserves raw mode, including a symlink/special-file mode or a permission-only mode; no synthetic `isSymlink`, resolved target, inode, uid/gid, atime, or optional metadata fallback is invented. SCP's no-follow policy must separately require matching regular-file/directory POSIX `S_IFMT` bits for every selected entry and traversed ancestor, rejecting missing kind bits, symlinks and special files rather than following them. An unrelated symlink in a directory must remain distinguishable without discarding the whole listing.

**Remaining prerequisite/limit:** no authorized private token/HAR or pinned private daemon implementation is available to prove the deployed metadata mode encoding or lstat semantics. A backend which follows symlinks before emitting indistinguishable regular-file metadata cannot be made no-follow by a client-side enum check. Even usable entry mode evidence is a preflight: these routes expose no atomic relationship between a metadata check and a later list/open/mkdir/move. A concurrent remote writer can change a component after inspection; neither this client nor the TLS fixture claims server-side race-free no-follow/exclusive creation.

### Shared HTTP byte limits

Inspection of `electron/portal-api/client.js` shows a **64 MiB default streaming response cap**, but no fixed 64 MiB maximum: an explicit positive safe-integer `maxBytes: 1073741824` permits a 1 GiB streamed response. The cap applies both to a declared Content-Length and counted bytes. JSON/text/empty response collection remains bounded by `min(maxBytes, 1 MiB)`; error bodies are separately bounded to 1 MiB, so extremely large directory listings are not silently unbounded. Streaming upload bodies are counted against their exact declared Content-Length, not the response `maxBytes`. Multipart overhead therefore does not reduce a file's payload limit in this shared client. Existing GUI/CLI default transfer limits are independent; SCP callers must explicitly opt into their larger limit. No shared-client change was required or made.

The local TLS fixture models the evidenced SSH directory listing/mode and lowercase type behavior, one-directory mkdir success/collision/missing-parent behavior, and stat-following type queries for links. It exposes raw symlink modes to test client refusal; it is not proof of private daemon behavior. Verified multipart framing/init/chunk/merge schemas above remain unchanged.

### Explicitly accepted limitations

The user approved official `fileExist` preflight semantics: existing destinations are rejected by default and overwrite requires explicit permission. This is **not atomic remote no-clobber**; another writer can race between checking and publication. Local final-file publication remains separately protected. The previous SSH/Base64 file-transport implementation must be removed, not retained as fallback.

Private temporary-directory ownership, sharing, expiry and safe deletion are not established. Cancellation must retain remote temporary state honestly instead of invoking generic deletion and claiming rollback. No automatic resume or reuse of unrelated existing chunks is implemented.
